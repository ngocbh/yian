VERDICT: NEEDS_REVISION

## Summary Assessment

The node-atomic direction is substantially simpler than checkpointed continuations, but the log is not yet specified as a crash-consistent state machine. Several current surfaces also cannot survive the proposed deletions without an explicit replacement or deletion decision.

## Critical Issues (must fix)

1. **The record vocabulary does not make every JSONL prefix a valid state.** `NodeFailed` followed by `RunFailed`, an END `NodeSucceeded` followed by `RunSucceeded`, and `NodeRouted` followed by one or more `NodeSkipped` records describe one reducer transaction as several durable records. A crash between them leaves an ambiguous nonterminal log. Conversely, one route currently mutates several edges/nodes and recursively skip-floods in one call (`runtime/engine.py:861-891`), so independently persisted `NodeSkipped` records would be redundant or partially applied. Define a minimal set of authoritative transitions where one appended record maps to one atomic reducer call; derive terminal and skip observer notifications from that transition. `RunResumed` may be an authoritative transition because it moves the ordered in-flight set back to ready. `RunSucceeded`, `RunFailed`, and `NodeSkipped` should either be derived views or be folded into the authoritative record that causes them.

2. **“Append, then apply” needs a prepare phase that makes reducer application infallible.** A succeeded output must be type-checked and converted to a `TypedValue` before append. More importantly, growth currently mutates the graph before checking the node budget (`runtime/engine.py:670-676`) and can still fail during depth stamping or graph bookkeeping (`runtime/engine.py:696-729`). Appending `NodeExpanded` and then discovering that it cannot be applied produces a log that cannot replay. Specify `worker outcome -> prepare/validate durable transition -> append+flush -> total reducer apply`. Preparation must validate the commit target, typed value, route handle, serializable grow seed/prune set, replayed subgraph, node/depth budget, and ID collisions without mutating `RunState`.

3. **The dispatcher must own dispatch, not merely enqueue.** The current pooled implementation puts IDs in a `queue.Queue`, workers remove them, and workers emit `NodeStarted` from inside `eval_node` (`runtime/engine.py:561-575`; `runtime/eval_node.py:67`). That worker-side dequeue is hidden mutable queue state and cannot satisfy the proposed single-owner `RunState` or exact ready/in-flight reconstruction. The revised design should say that the dispatcher pops its own ready deque, appends `NodeStarted`, applies ready-to-in-flight, and only then submits the node to a worker. A submit failure is then an unfinished start and is safely retried. Worker outcomes alone return to the dispatcher. This also gives a precise, durable dispatch order for requeuing unfinished nodes.

4. **Parallel terminal failure is undefined when sibling workers cannot be cancelled.** With blocking `ask_user` and timed waits, one worker can wait indefinitely while a sibling fails or the log append raises. Python cannot kill the blocked stack. Returning `RunFailed` immediately leaves a live prompt/tool call that may later produce side effects or attempt to report into a closed run; waiting for all workers can prevent a terminal failure forever. The current engine already joins only for two seconds after fail-fast (`runtime/engine.py:260-264`), but making blocking input ordinary greatly increases this case. Choose and document one policy, including log semantics: structured draining of all in-flight nodes, cooperative cancellation for engine-owned blocking operations plus explicit detachment of arbitrary calls, or another enforceable lifecycle. Add fail-plus-blocked-human, fail-plus-sleep, and append-failure-plus-in-flight tests.

5. **`RunStarted` does not contain enough state for equivalent recovery.** `run_flow` seeds `${system.today}`, `${system.now}`, and `${system.run_id}` before execution (`run.py:211-214`); replay must restore those exact typed values rather than seed a new clock. Effective LLM configuration is also applied by mutating the compiled graph before execution and currently must be supplied again on durable resume (`run.py:207-209`, `run.py:329-335`). Persist the complete initial `VariablePool` (or all system ambients plus coerced inputs) and define whether the effective run configuration is recorded or must be supplied and fingerprint-validated. The private graph copy must be made before `resolve_llm_cascade`, otherwise fixing growth mutation still leaves `ComposedFlow` mutated. Also define a stable fingerprint algorithm covering nested child flows; no such mechanism exists today.

6. **Deleting `Pause` is incompatible with the stated deferred scope.** `WaitNode` has only two behaviors and both return `Pause` (`nodes/wait/node.py:102-108`). Timed WAIT can be rewritten to block, but event/watch WAIT has no blocking provider and cannot remain while `suspension/` and `Pause` are deleted. Remove the unreachable event mode in this change or specify an injected blocking event implementation. Likewise, the claimed closed log/observer vocabulary omits current `StreamChunk` and `RunAborted`, while the design explicitly defers streaming deletion and never decides the fate of `request_abort` (`events.py:130-137`, `events.py:269-273`, `runtime/engine.py:200-202`). Either delete those surfaces now or keep a clearly separate transient observer vocabulary; “one vocabulary” is not currently true.

7. **The shared `ask_user` registry contract is underspecified and does not yet support both callers.** The agent calls a one-field LangChain tool (`question`), while structured `HUMAN_INPUT` carries `prompt`, a question list, `answer_schema`, title, and node identity (`nodes/human_input/node.py:70-100`). A normal `StructuredTool` validates invocation against one callable signature. Define the exact registered input/output schema that accepts both forms and what schema the model sees. Also define registration lifetime: the existing process-global registry rejects duplicate IDs (`tools/registry.py:50-56`), so “CLI registers it” and “library hosts register their own” cannot both work sequentially without an explicit replace/unregister policy or strict host-only ownership. The CLI prompt lock must coordinate with its progress renderer, not only with other prompts, because the prompt now runs inside a worker.

8. **JSONL recovery needs file ownership and physical repair.** Ignoring an unterminated final line in memory is insufficient: appending after that fragment concatenates the next record onto corrupt bytes. Under an exclusive writer lock, recovery must truncate back to the last newline before appending. Fresh runs should create the log exclusively, and resume must prevent two processes from validating the same last sequence and appending the same next sequence. Without that, contiguous sequence validation does not protect the single-writer invariant.

9. **`RunState` omits derived growth state required after replay.** Current growth behavior relies on per-node reference depth to enforce `MAX_REF_DEPTH` (`runtime/engine.py:179-181`, `runtime/engine.py:800-820`) and on per-run START wiring overrides (`runtime/engine.py:157-162`). The checkpoint-only nested-ledger maps can disappear, but depth and any remaining growth traits must be fields of `RunState` or be provably derived during every `NodeExpanded` fold. Otherwise a resumed nested call can observe different limits than the uninterrupted run. The design should enumerate authoritative state versus replay-derived indexes rather than claiming the current list is exhaustive.

## Suggestions (nice to have)

- Keep raw worker outcomes, durable records, and observer notifications as three small semantic roles even if they reuse data classes. Forcing `NodeExpanded(Grow)` and `StreamChunk` into the same durable union makes the boundaries less clear, not more concise.
- Have the reducer return derived observer notifications after a successful apply. This preserves ergonomic plain outputs for `on_event` while the durable record can carry a typed wire value.
- Record the selected worker count on every resume boundary when `num_workers` overrides the original value.
- Create CLI log files with restrictive permissions and document that prompts, human answers, tool outputs, tracebacks, and model output may contain secrets.
- Test recovery after every authoritative record prefix, including every record in nested CALL/MAP/LOOP runs. Compare graph nodes/edges/wiring, pool, dispositions, ready order, in-flight order, growth depth, and terminal result, not only final output.
- Clarify that a flow fingerprint detects authored/compiled identity, not changes to external tool implementations, imported Python callables, model services, or environment defaults.

## Verified Claims (things you confirmed are correct)

- A private per-run graph is necessary. `FlowEngine` stores and mutates the supplied `CompiledFlow` directly (`runtime/engine.py:147`, `runtime/engine.py:670-673`), and `resolve_llm_cascade` also mutates agent configuration and child references before the engine starts (`compile/llm_cascade.py:24-50`).
- The existing positive-`num_workers` path already has a single dispatcher for graph, edge, and pool mutations, while workers only evaluate nodes and return events (`runtime/engine.py:526-575`). Retaining parallel execution is compatible with a dispatcher-owned durable reducer.
- CALL, MAP, and LOOP already expose node-owned replay builders and serializable-looking seeds (`nodes/call/node.py:68-91`, `nodes/map/node.py:94-111`, `nodes/loop/node.py:106-119,170-180`). Flat chronological expansion records with explicit prune sets can replace the nested ledger, provided seed values use the typed codec and application is prepared before append.
- The agent continuation path is genuinely large and special-purpose: `Fresh | Resume`, agent spawner traits, control interception, memo serialization, and a synthetic HUMAN_INPUT/resume subgraph are all present (`nodes/agent/node.py`, `nodes/agent/modes/tool_calling.py:72-171`). Blocking the ordinary tool invocation removes that machinery.
- The normal tool registry is process-global and is already shared by TOOL nodes and agent tool calling (`tools/registry.py`, `nodes/tool/node.py:37-45`, `nodes/agent/modes/tool_calling.py:58-69`). Moving `ask_user` there is structurally feasible once its shared schema and registration ownership are explicit.
- `VariablePool` already provides a tagged, JSON-round-trippable representation for stored node and system values (`typesys/pool.py:35-68,130-138`), so it is the right primitive for log payloads and initial run state.
- The proposed package dependency direction can remain acyclic if `events.py` stays a leaf data vocabulary, `runtime/log.py` depends on events/typesys only, `runtime/state.py` owns the reducer, and `run.py` owns filesystem policy. The design should preserve that direction when implementing the missing codecs and fingerprinting.
